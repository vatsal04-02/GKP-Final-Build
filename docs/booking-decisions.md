# Booking: decisions recorded after Slice 3 review

## Decisions on the Slice 4 plan (approved; these OVERRIDE anything below or in `docs/slice4-plan.md` that differs)
- **D1 Consent permissions.** Explicit per-user grant only. Admins can record, correct and revoke consent. Front desk and doctors need an explicit grant to record **Yes**. Any authorised staff member can record **No**. AI and n8n can never grant consent or convert Unknown to Yes.
- **D2 Registration form.** The existing website checkbox is **NOT approved** as reminder consent. The registration form is still pending the owner's review (to be supplied separately). **No consent migration or backfill before that review.** Generic inbound WhatsApp consent is not reminder consent. A signed form counts as evidence only if it contains a clear affirmative WhatsApp appointment / treatment reminder clause, identifies the clinic and explains withdrawal. Existing register patients: inspect the actual wording first; clear evidence keeps the form reference, signature date and source; missing or ambiguous = Unknown; never bulk-convert patients or leads to Yes.
- **D3 Booking confirmations.** A separate transactional purpose, independent of appointment-reminder consent, but bound by Meta's opt-in, template and 24-hour customer-service-window rules. A booking request is not blanket consent for future reminders or marketing. No outside-window business-initiated template without the required permission.
- **D4 Implied consent.** Patients whose only evidence is that they messaged first, or the unapproved website checkbox, stay **Unknown** for appointment reminders: suppress until explicit evidence is recorded. Existing opt-outs always win.
- **D5 Deployed workflow export.** Read-only inspection only. Strip credentials, API keys, tokens, auth headers, patient information, message histories and sensitive webhook URLs. Never activate, edit, re-import or execute exported workflows.
- **D6 Audit outbox.** On the `flowhq_config` persistent volume, subject to verifying persistence across container recreation and restarts. **Fail closed** if the write-ahead intent cannot be durably saved before an appointment mutation. Include locking, permissions, disk-full handling, corruption recovery, backup and forced-termination recovery tests.
- **D7 Order.** 4A (audit outbox) then 4B (consent) then 4C (workflows) then 4D (calendar). Stop for review after each sub-slice.
- **Status (updated).** 4A (audit outbox) and 4B (reminder consent) are implemented and tested. 4C (n8n) is **built as a new repo candidate and tested in the simulator only** (`docs/n8n-4c-changes.md`); the deployed workflows were never exported, so it is unverified against production (`docs/n8n-deployed-export-procedure.md`). 4D (calendar views) is NOT started. ## 1. Pending appointments get no reminders  (decision: recorded; W5 change designed, NOT made)
- A **Pending confirmation** appointment must not receive W5 reminders. A **Confirmed** one proceeds to the normal eligibility checks.
- `Appointments.Status` is untouched (W4-W9 compatibility). Pending is `Status = Booked` + `Appt_Stage = Pending confirmation`, so today W5 (which only tests `Status === 'Booked'`) WOULD remind it. The fix is one extra condition in W5's candidate step:
  `if (f.Appt_Stage === 'Pending confirmation') continue;`   (blank stage = every legacy / Cal.com row = unchanged; "Checked in" is irrelevant to a future reminder window).
- Legacy behaviour is preserved by construction: rows without `Appt_Stage` take exactly the old path. Test: a legacy Booked row with and without the new column produces identical candidates.
- When staff move Pending to Confirmed the row becomes eligible; the normal time windows still apply (confirmed after the 24 h window has passed = only the 2 h reminder).
- Skips are counted, not logged per row (W5 runs every 15 minutes): one `Run_Log` summary line per day ("N pending appointments not reminded"), the same pattern W15 uses.

> **Superseded in part by `docs/slice4-plan.md`.** A workflow audit found that the deployment-candidate W12 DOES enforce `LEADS.Consent_WhatsApp` for business-initiated templates (the older `n8n/workflows/W5` and `wa-send.js` do not), that existing consent is only generic (`whatsapp-inbound`, draft website wording), and that no message purposes exist. Consent is now planned as a per-phone table with an append-only history (not fields on each appointment), and the audit outbox gains a mandatory write-ahead intent. Where this file and the plan differ, the plan wins.

## 2. Reminder consent is explicit, never assumed  (decision: recorded; design below, NOT built)
Booking at the clinic does **not** grant consent for automated WhatsApp reminders. Unknown and No suppress reminders. Unknown is never silently turned into Yes.

**What the repo shows about today's consent.** `LEADS.Consent_WhatsApp` (a Toggle on the lead) is enforced by W15 (`followup-reminder.js`: `Consent_WhatsApp !== true` means held; a missing value counts as no consent) and `grist/schema.md` says W12 applies it to business-initiated templates. **Not verified:** I found no `Consent_WhatsApp` check in W5, W12 or `wa-send.js` in this repo, so W5 reminders to lead-linked patients may currently go out without a consent check. Confirm against the deployed workflows before relying on it. This is the existing behaviour to preserve (not tighten silently); making W5 respect it is part of the W5 change.

**Proposed fields** (additive columns on `Appointments`, added by `provision-booking`; a blank value means **Unknown**):
| Column | Values |
|---|---|
| `Reminder_Consent` | `Yes` / `No` / `Unknown` (blank = Unknown) |
| `Reminder_Consent_At` | DateTime the answer was recorded |
| `Reminder_Consent_Source` | `Patient replied on WhatsApp`, `Told staff in person`, `Told staff by phone`, `Signed form`, `Legacy lead consent` (copied from `Consent_WhatsApp` only by an explicit staff/admin action, never automatically) |
Consent is stored on the appointment as a snapshot of what the patient said when booking, because most bookings have no Lead or register patient to hold it, and the same phone may change its answer.

**Effective rule W5 would apply** (first match wins):
1. Any lead with the same normalised phone has `Opted_Out` ticked, or ANY appointment for that phone has `Reminder_Consent = No` (a withdrawal wins): **suppress**.
2. Appointment linked to a Lead (all legacy rows): **legacy behaviour unchanged** (the lead's own consent / opt-out data, as W5 / W12 treat it today). Where the lead has `Consent_WhatsApp = true` that counts as `Yes` with source `Legacy lead consent`.
3. No Lead: send only if `Reminder_Consent = Yes`. `No` or `Unknown` or blank: **suppress** and count it (daily summary line, as in #1).
Prior consent is never copied forward silently: when staff book again for a phone that previously said Yes, the form can SHOW it ("said Yes on <date> via <source>") and staff must tick to reuse it.

**CRM changes it needs** (a later, approved slice): the three columns; staff booking form selector ("Patient agreed to WhatsApp reminders: Yes / No / Not asked", with source, default Not asked = Unknown); consent shown and editable (audited, who / from / to, no phone) in the appointment drawer; the API's `GET` returns the three fields; AI `POST /appointments` accepts an optional `reminder_consent` ONLY with a source of `Patient replied on WhatsApp` and defaults to Unknown (the assistant must not assert consent the patient did not give, and a patient messaging the clinic is not by itself consent to template reminders). W5 fixes are in `docs/booking-integration-gaps.md`.
**Tests it needs:** blank / Unknown / No suppress; Yes sends; a later No suppresses earlier Yes appointments for the phone; opt-out by phone suppresses; a lead-linked legacy row behaves exactly as before; Unknown is never written as Yes by any code path (property test over create / reschedule / status / import); consent change audited without the phone.
**Open question for the owner:** is a signed registration form with a WhatsApp-reminder clause acceptable as source `Signed form` for existing register patients, and who may record `Legacy lead consent`?

## 3. Durable audit outbox  (decision: design only, NOT built)
Problem with today's in-memory retry queue: a restart loses waiting entries, and a retry after a half-finished write could create a duplicate.

**Design: a local write-ahead outbox file plus an idempotent flush.**
- **Where:** `config/audit-outbox.jsonl` on the existing persistent `flowhq_config` Docker volume (already mounted writable for workspace profiles). Not in Grist: a Grist outage is the very failure it must survive. (A second Grist table or SQLite were rejected: same failure domain / a new native dependency; an append-only file is enough for a single process.)
- **Entry:** one JSON line: `{ audit_id (UUID made when the event happens), seq (monotonic), at, actor, source, action, record, outcome, reason, detail }`. The same rows that go to `Booking_Audit` today, still without names, phones, free text, idempotency keys or secrets.
- **Write path:** `audit()` appends the line and `fsync`s it BEFORE returning (microseconds, no network). Only then does a background flusher write to Grist. The appointment itself is already saved and verified by that point, and **an outbox or Grist audit problem can never turn a verified appointment into a reported failure**: the booking response is unchanged; the problem is surfaced as an admin alarm.
- **No duplicates:** add `Audit_ID` (Text) to `Booking_Audit`. The flusher (one at a time, under its own mutex) reads the existing `Audit_ID`s, inserts only entries not yet present, reads back to VERIFY, and only then marks them done by atomically rewriting the file (write temp, fsync, rename). A crash between insert and mark-done just means the next flush sees the id already present and skips it.
- **Restart:** on start the outbox is loaded and flushed in the background (retry with backoff, also on the next audit write). A truncated last line (crash mid-append) is detected and ignored, with a warning, never crashing startup.
- **Visibility to admins:** the Schedule page banner and `GET /schedule/overview` show waiting count, oldest entry age and last error; amber after 5 minutes or 20 entries, red after 30 minutes or 100, plus an `AUDIT OUTBOX` error line in the server log (no PII) that the existing log monitoring / W11 style alerting can watch. Entries are **never dropped** to make room: past a size cap it alarms louder; it does not discard.
- **If the outbox itself cannot be written** (disk full / read-only volume): the saved appointment still stands and is reported as saved; the admin alarm is red, and an admin can set a "pause new bookings while audit is down" policy (off by default; the pre-write check is the only place that would refuse a booking, never after the fact).
- **Optional phase 2 (write-ahead intent):** append an `intent` line BEFORE the Grist write and an `outcome` line after, and on startup reconcile any intent with no outcome by looking the booking up (by `Idem_Key` / reference). This also covers a crash between a verified write and its audit line. Recommended, not required for phase 1.
- **Single process:** the same documented assumption (one FLOW HQ instance); the file is not safe for two writers.
**Tests it needs:** survives a restart (new service instance reads the file and flushes); crash between Grist insert and mark-done gives no duplicate (`Audit_ID`); flush retried while Grist is down, visible counters and alarm levels, order kept by `seq`; truncated last line tolerated; outbox write failure does not fail or mislabel a saved appointment; no PII or key in any line or log (extend the existing scan); backfill of `Audit_ID` for older rows not required (they have none and are never re-sent).

## 4. Doctor identity is a stable Doctor_ID  (decision: DONE and tested)
- A doctor's login is now bound by **`doctorId`** (the stable `Doctors.Doctor_ID`, e.g. `DR-001`) in `config/users.json` (see `config/users.example.json`). Booking rights for a doctor's login follow that id and nothing else.
- The older name-only (`clinician`) logins still work **only** through an exact match (case and spacing ignored) to exactly one doctor: a transitional fallback so existing logins keep working. **No partial / "contains" matching**: `Mahesh` alone gets no write rights. A `doctorId` that is not a real doctor also gets none (even if the name would have matched). A doctor login with no resolvable doctor can view but not change anything, and is told to ask the admin to link it.
- The page no longer guesses from names: `GET /schedule/overview` returns `me: { doctor_id, is_doctor_login }`, resolved on the server, and the appointment drawer compares `appointment.doctor_id` with it. **Server-side authorization stays authoritative**; the buttons are only a convenience.
- Loose name matching still exists, correctly, only for DATA: attaching an older Cal.com / W4 row (which only has a `Physio` name) to a doctor so its time is not double-booked. It never grants any right.
- Action for the admin before real doctor logins are used: add `"doctorId": "DR-001"` (etc.) to each doctor's entry in the server's `users.json`. Not done here (that file is not in the repo).
- Tests (`tests/booking-staff.test.ts`): id wins over name, vague name, bad id, exact-name fallback, admin / desk are not doctor logins.
